The F7 rescind/fix history below is retained deliberately — it is the evidence that this freeze was earned by attack, not by agreement.

> **F7 (freeze blocker, RFC #40, empirically confirmed):** §2.1 names the `Actuator.CommitToken` invariant as *"at most one valid execution authorization for an irreversible effect identity E,"* but neither S1–S9 nor the formal model enforces its **consume-once, cross-epoch** nature. Trace: `C0` authorizes effect `E` (op A); `C0` legitimately reconfigures to unique successor `C1`; `C1` authorizes a **conflicting** outcome for the *same* `E` (op B). `NoConflictingAuthority` permits conflicting ops under *comparable* configs — which is correct for **revisable** authority (a successor legitimately changing a mutable decision) but wrong for a **consume-once** effect. `formal/check_authority.py` reports `violations=[]` for the reachable trace `accepted={(C0,A),(C1,B)}` — a false green. **Root cause:** the contract conflates two invariant classes under one rule; config-supersession is not outcome-supersession. **Required fix (gate item 22):** distinguish *revisable* vs *consume-once* authority; for a consume-once key, forbid conflicting outcomes across **all** configs (not only incomparable ones) — once a valid token exists for `E`, no config (successor or not) may authorize `E` again absent explicit operation-level cancellation/non-execution evidence. ## 1. Consensus is a cost, not a plane

The predecessor's instinct — and this project's own first framing (#26) — was to draw an "Authority Plane" as a fixed set of operations. That is wrong. **Coordination is a per-operation cost, paid only where an operation's exact invariant is provably not coordination-free.** The CP set is *computed*, never declared.

```text
Coordination-free by default.
Quorum only for irreducible non-monotonic authority.
```

The three surfaces (#26) remain useful as *dissemination/durability* roles — Evidence (append-only causal), Authority (the computed CP subset), Awareness (interest-based gossip) — but "authority" names an *outcome of analysis*, not a bucket ops are assigned to by intuition.

## 2. The coordination-avoidance test

For every authority-relevant operation, membership in CP is decided by **invariant confluence** (Bailis et al.), not by object type:

```text
operation → exact invariant → monotonic? → I-confluent under the proposed merge?
  → if not: can the invariant be decomposed / escrowed / preallocated?
  → smallest coordination domain → partition behavior → receipt requirement
```

A non-I-confluent operation is **not** automatically global consensus: first try to localize it (per-`authority_key` serialization, escrow, reservation, bounded lease). Only what remains irreducible pays for quorum. *Do not coordinate farther than the invariant requires.*

### 2.1 Classification (evidence basis, from R5; hypotheses proven or held)

| Operation | Invariant | Class | Domain / mechanism |
|---|---|---|---|
| `observation.recorded`, `claim.recorded`, evidence attach | append-only monotone | **AP** | none (local) |
| `same_as_candidate`, read-equivalence projection, local representative | equivalence join-semilattice + deterministic representative | **AP** | none (local projection, #28) |
| `canonicalizes_to` (authority-merge) | changes the future authority target / lineage of `authority_key` | **CP** | the Cell (fix F2 — #28 governed act, **not** AP) |
| trust-for-evidence (#21) | per-evaluator subjective projection over a G-Set of accusations | **AP** | none (local) |
| `capability.exercise` / `approval.consume` — **fungible** (divisible quota/escrow) | act within a divisible pre-issued allocation; `Σ exercise ≤ allocation` | **AP\*** | within a disjoint pre-issued pot (partition-safe by preallocation) |
| `capability.exercise` / `approval.consume` — **singular consume-once** (non-fungible token) | `Σ consumptions(token) ≤ 1` across the whole system (F8, RFC #41) | **CP or node-pinned lease** | approver Cell quorum, **or** an epoch-fenced, non-transferable exclusive lease pinned to one node id — *not* plain AP\* |
| `capability.issue / refill / revoke`, `approval.grant / revoke` (#32) | grant/withdraw standing authority | **CP at issuance** | issuer/approver Cell (fix F6) |
| plan successor (uncontested) | fork-join DAG + Sagas compensation | **AP\*** | local; converge or compensate |
| single-writer cutover (cooperative) — **reconcilable stream writes only** | linear handover of append-only Domain writes (divergent branches preserved & reconciled, #52) | **AP\*** | predecessor→successor signature chain; equivocation → CP fencing |
| single-writer cutover gating an **irreversible external effect** | strict exclusivity before a non-reconcilable effect (F9, RFC #41) | **CP** | this *is* an `Actuator.CommitToken` (consume-once); reactive equivocation-fencing is too late once the effect fired |
| **`Cell.EpochSuccession`** | no two incomparable configs authorize conflicting transitions for `K` | **CP** | the Cell (quorum) |
| **`Actuator.CommitToken`** (consume-once) | **at most one valid execution *authorization*** for an irreversible effect identity `E`, **across all epochs/configurations** — a legitimate successor may NOT re-authorize `E` (F7, RFC #40) | **CP** | actuator guard cell (quorum); consume-once, not revisable |
| trust-that-removes-an-authority-holder | changes authority standing | **CP** | folds into `Cell.EpochSuccession` |
| single-writer cutover (contested) | fencing against split-brain | **CP** | target Cell (fencing receipt) |

**AP\*** = coordination-free *on the hot path, within a pre-coordinated allocation*. Escrow/lease/capability delegation **amortize** coordination; they do not erase it. The allocation and the root descend from the one CP root (`Cell.EpochSuccession`) by offline signature chains. So after aggressive redesign the **provably-irreducible CP set is small**: reconfiguration of authority, and the terminal irreversible commit. Everything upstream (planning, approval, delegation) is speculative/compensable — which is exactly Kawa's "intent ≠ execution ≠ verified result."

Honest trade: a lease/capability revoked during a partition stays usable until its (short, assurance-gated per #30) TTL expires; the `Actuator.CommitToken` CP gate is the hard backstop, so even an unexpired stolen right cannot commit an irreversible effect without the actuator quorum — **and the actuator MUST reject stale authority at effect time** (an expired/superseded right presented at commit fails closed; the backstop only holds if the actuator actively checks, vendor-A review). A TTL is evaluated against clocks, so the honor-past-expiry window is bounded by the maximum tolerated clock skew **Δ_max, which is a policy-declared, `policy_digest`-pinned bound**: a right can be honored at most Δ_max past its intended expiry, never unboundedly (gate item 12; `formal/check_lease_skew_bound()`). Beyond Δ_max, and for any irreversible effect regardless of skew, the `Actuator.CommitToken` standing re-check is the authority — not the clock.

Two further hardenings from review:
- **Allocation is CP at issuance.** The escrow/lease/capability grants that make AP\* possible are themselves authority acts; **issuing / refilling / revoking them is CP**, not AP. Under contention or membership churn, on-demand allocation leaks coordination back onto the hot path — so the amortization is real only when allocations are provisioned ahead of the partition, and the *issuance* is classified CP, never hidden under AP\* operation (vendor-A review).
- **Cooperative single-writer cutover escalates on equivocation.** The AP\* signature-chain handover assumes a non-equivocating predecessor. If a partitioned/adversarial writer signs handovers to two successors, it **immediately degenerates to contested cutover = CP fencing** at the target Cell — the spec requires this escalation, it is not optional (vendor-B review). **But escalation is reactive (F9, RFC #41):** it is sufficient only for *reconcilable* Domain writes (divergent branches are preserved and reconciled, #52). Any **irreversible external effect** guarded by a cutover must be gated as an `Actuator.CommitToken` (consume-once, CP) *before* it fires — reactive fencing cannot un-fire a non-reconcilable effect.
- **Invariant class is load-bearing: revisable vs consume-once (F7/F8, RFC #40/#41).** An authority operation is either **revisable** (a later, legitimate configuration may change the decision — `Cell.EpochSuccession` target, `canonicalizes_to`; the default S1 rule applies) or **consume-once** (an outcome, once authorized, is permanent). Consume-once splits again by fungibility: a **fungible** quota is safely AP\* by disjoint preallocation (a divisible escrow partitions into pots); a **singular non-fungible** consume-once authority (`Actuator.CommitToken` for effect `E`; a one-time `approval.consume` token; exclusivity before an irreversible effect) is **CP or a node-pinned exclusive epoch-lease — never plain AP\***, and its uniqueness holds **across all configurations**, because **config-supersession is not outcome-supersession**. Checked in `formal/check_consume_once_authority()` with the C0→C1 double-authorization as the discriminating negative control.
- **`Actuator.CommitToken` authorizes; it does not assert physical exactly-once (fix F5, external review).** A quorum can guarantee **at most one valid execution *authorization*** for an effect identity E — it cannot prove a remote, non-transactional system physically executed E exactly once (crash-after-effect-before-Result is irreducibly ambiguous). The Core invariant is authorization-uniqueness. The trusted Adapter uses the token / effect digest as an **idempotency key where the target supports it**; where it does not, the outcome stays epistemically honest — `AUTHORIZED / EXECUTION_UNKNOWN / OBSERVED_SUCCESS / OBSERVED_FAILURE` — never silently converted into a false exactly-once claim. This is Kawa's own *intent ≠ execution ≠ verified Result* (spec §16).

## 3. The Authority contract (algorithm-independent)

The stable contract is a semantic relation, never a named algorithm (Raft/HotStuff/PBFT/FROST/BLS/`3f+1`/`epoch++` are replaceable profile mechanics, §8). It is machine-checked in `formal/AuthorityContract.tla` (+ the runnable `formal/check_authority.py`). Safety invariants:

```text
S1 No conflicting authority   — for one irreducible invariant, two conflicting successors
                                cannot both be valid unless one validly supersedes the other.
S2 Legitimacy is inherited    — except Genesis / explicit recovery, a valid configuration
                                needs a valid prior basis + valid succession proof. Higher
                                clocks/epochs/leader claims cannot mint authority.
S3 No dual sovereignty        — once C_new legitimately supersedes/dominates C_old for K,
                                C_old cannot later produce a conflicting valid receipt.
S4 Leader ≠ authority         — a temporary leader affects proposal/order/liveness only;
                                the quorum proof creates authority.
S5 No stale resurrection      — learning an old cryptographically valid proof cannot roll
                                current authority standing backward.
S6 Clocks ≠ authority         — wall clock / HLC / occurred_at cannot alone make an
                                operation authoritative (#36: clocks suggest, references prove).
S7 Distrust is forward-only   — compromise changes current/future standing; it never rewrites
                                that a receipt was historically valid under its then-basis (#21).
S8 Recovery ≠ reconfiguration — if the legitimate predecessor cannot authorize a successor,
                                never silently lower quorum or fabricate lineage (§7).
S9 Independent domains        — loss of quorum for K1 does not block unrelated K2 unless an
                                explicit cross-key invariant couples them.
```

Three separations are load-bearing: **cryptographic validity ≠ lineage validity ≠ current authoritative standing.** A quorum certificate from a stale/superseded/forked configuration can be cryptographically valid and confer no current authority.

A fourth separation is load-bearing after RFC #40/#41 (F7/F8): **revisable authority ≠ consume-once authority.** S1's "two conflicting successors cannot both be valid unless one validly supersedes the other" is stated for *revisable* authority, where a legitimate successor may change a mutable decision. For a **consume-once** authority — an irreversible `Actuator.CommitToken` for effect `E`, a singular `approval.consume` token — **config-supersession is not outcome-supersession**: once `E` is authorized, no configuration (successor or not) may authorize `E` again, absent explicit operation-level cancellation/non-execution evidence. S1 therefore reads, for a consume-once key, as *"at most one authorization for `E` across all configurations."*

The cancellation/non-execution escape hatch is safe **only as a first-class, verifier-checked (CP) authority proof**, never an AP claim (re-review hardening, RFC #40 lane): it MUST bind `(E, prior_token_digest, policy_digest, lineage_frontier)` and prove the prior authorization was authoritatively canceled or never became exercisable. Absent such a VALID proof, the state is *consumed* (or `INCOMPLETE`), never reusable — a forged or local-only cancellation confers nothing. Two further precisions: **rollback ≠ non-execution** — once `A` was a valid authorization, the consume-once invariant is spent even if the world later compensates (F5: authorization-uniqueness, not physical exactly-once); a fresh attempt after rollback must use a new effect identity `E'` or a valid never-exercisable proof for `A`. And **when reversibility is unknown, the safe class is consume-once/CP** until the target adapter supplies a policy-pinned proof of reconcilability/idempotency — optimism about compensability is not a classification. (The generic model checked S1 for revisable keys and tolerated the cross-epoch double-authorization; `formal/check_consume_once_authority()` closes it, with the C0→C1 succession trace as the discriminating negative control.)

## 4. Configurations and succession

Authority is held by a **configuration** (a set of members with a quorum rule for an `authority_key`), and it moves by **proven succession**, not by a location or a permanent node.

> **Authority persists through a verifiable succession chain; members do not.** (the distributed-consensus form of #30's "no permanent Trust Authority node")

- **The Core invariant is semantic; succession is comparability-preserving (fix F3; gate 17 resolved by profile scoring).** Core requires: **no two non-dominated / incomparable authority configurations may simultaneously confer conflicting current authority for the same authority domain**, AND — the resolution of gate 17 — **every legitimate configuration is dominance-comparable to the current authoritative one; concurrent incomparable authoritative fronts are not a Core-conforming state.** The algorithm-independent property is realizable by *unique successor / linear succession* (default), *joint consensus* ($C_{old}\oplus C_{new}$), forward-secure supersession/fencing, or *statically-verifiable heterogeneous-quorum* reconfiguration — all of which preserve a single comparable front. **A genuine partial-order lattice / dominance reconfiguration (concurrent incomparable fronts) is non-conforming**: the profile-scoring lane (vendor-B,) produced a surviving refutation — an offline verifier cannot determine the authoritative frontier without a live oracle or an external total order, and recording the join as a strict event-log ordering degenerates back to linear succession while leaking a frontier-DAG into the Receipt (Core abstraction breach). **The formal model's chain-based `Comparable()` already encodes this commitment**; the unique-successor realization (a config superseded by at most one successor) is the simplest sufficient profile, joint-consensus the exhibited alternative (gate 14) — a swap between them needs no Core edit.
- **Unique authoritative succession (proven by the model, PR #39; sharpened by vendor-A review).** Quorum overlap with the *parent* is **not** sufficient: two successors can each overlap the parent by a quorum yet be mutually incomparable, letting one parent authorize two divergent lines. Therefore **a configuration may be superseded by at most one successor**. Crucially, "at most one" is **achieved by quorum agreement, not assumed** — the reconfiguration *is* the CP `Cell.EpochSuccession`, in which the parent's quorum agrees on exactly one successor (the model checks the property given the guard; the contract requires the guard to be a consensus outcome). It further requires **quorum intersection across the transition** (honest members carry from parent to successor) and **invalidation of stale successor certificates** (a losing/superseded proposal's cert never confers standing, S5). Together these make S1/S3 hold over reconfiguration traces; the model reproduces the split-brain the moment the uniqueness guard is dropped.
- **no-master ≠ leaderless.** Kawa forbids a permanent master / caste / irreplaceable coordinator, **not** a transient elected leader/proposer. Leadership orders and proposes; the quorum proof confers authority (S4).
- **Fluid membership** (#26/#20): a peer that becomes stable/high-assurance may rotate into a Cell; one that degrades rotates out — a node-lifecycle transition, itself an `Cell.EpochSuccession`. No node is a superior; the Cell is a role, not a caste.

## 5. The Authority Receipt

A CP operation's acceptance is a committed Event **carrying a quorum proof** — the Receipt (#36). It is a *proof about* an Event, never a second Domain SoT.

```text
AuthorityReceipt {
  authority_key
  operation_digest
  configuration_id
  authority_epoch
  configuration_digest
  prior_authority_receipt_digest   -- binds configuration lineage
  prior_authority_frontier_digest
  policy_digest                    -- content-addressed (§6)
  approval_digest?                 -- for approval-bound ops (#32)
  quorum_proof
}
```

The proof relationships are the contract; field names are illustrative. A verifier can prove *this operation was accepted by the legitimate configuration for this epoch, descending from the prior legitimate configuration* — without trusting a mutable `current_members` table.

### 5.1 Three-state verifier
```text
VerifyAuthorityReceipt(r, local_proof_store) → VALID | INVALID | INCOMPLETE
```
- **VALID** requires statement binding + configuration proof + quorum/profile proof + **lineage standing under the currently-authoritative epoch** + pinned policy + approval binding where applicable. A quorum certificate that is *cryptographically* valid but sits under a **stale, superseded, or forked** configuration is **not VALID** — it is INVALID (if evidence proves the config was superseded) or INCOMPLETE (if the current lineage is not locally known). This is the crypto ≠ lineage ≠ standing separation (§3) applied to the verifier, and it is the S5 (no stale resurrection) guarantee at read time (vendor-A review).
- **INVALID** = available evidence proves failure (bad proof, wrong key, operation mismatch, invalid/superseded lineage, binding mismatch).
- **INCOMPLETE** = the local verifier lacks a required durable proof (predecessor/succession proof, historical verifier material, policy artifact, recovery anchor). `INCOMPLETE ≠ VALID ≠ INVALID`; it is **absorbing w.r.t. safety** — it may become VALID only after fetching *and* validating the exact `configuration_digest` + `prior_authority_receipt_digest` chain under the current epoch, never by assumption. It may be stored/disseminated but **cannot exercise authority**.

This is the authority-side twin of Fact's `clear/conflicted/unknown` (spec §5.3), of the read-frontier completeness (N5), and of #36's Interpretation Receipt — one epistemic pattern: *unknown is neither false nor authority.*

## 6. Policy is a content-addressed input

`Understanding = f(events, policy, reducer, schema)` is deterministic only if policy is immutable and pinned. A numeric `policy_version = 17` is worthless if v17's bytes can change.

```text
policy_digest = H(canonical PolicyBundle)        -- JCS / RFC 8785 canonicalization (#32)
policy.established(policy_digest) / policy.superseded(A → B)   -- authority is event-sourced
```
Genesis (#30) is the base case (`initial_policy_digest = P0`); all later policy authority descends from explicit Events. Every Authority Receipt and Interpretation Receipt pins the exact `policy_digest` it was evaluated under, so cross-implementation equivalence (⑦) and stale-approval detection (#32) are defined against immutable bytes, not a mutable label.

### 6.1 In-flight operations across policy supersession (freeze blocker — vendor-B review)
Content-addressing fixes *which* bytes a decision used, but not *whether a decision begun under policy A may commit after `policy.superseded(A → B)`*. An operation carries the `policy_digest` it was **initiated** under; the CP commit fence (`Actuator.CommitToken` / `Cell.EpochSuccession`) MUST re-check it at effect time against a defined rule, one of: (a) **reject** — an op whose pinned policy is no longer authoritative at commit fails closed and must be re-initiated under B; or (b) **bounded grace** — a policy MAY declare an explicit, digest-pinned validity window during which in-flight A-ops may still commit, after which (a) applies. The default is (a) reject. What is forbidden is the current silence: an undefined fence lets an A-initiated irreversible commit land after B forbade it. AP evidence ops are unaffected (they carry no authority); only CP-fenced operations consult the fence.

## 7. Partition and catastrophic recovery

- **Partition:** Evidence/Claim (AP) work continues; an affected `authority_key` **blocks** its CP transitions (fail-closed, never split-brain, S3); unrelated `authority_key`s continue (S9). Two partitions can never both produce valid conflicting receipts for the same key/epoch.
- **Catastrophic quorum loss** (no legitimate live quorum can produce a succession proof): the only honest options are (1) stay blocked for that domain, (2) restore enough legitimate prior authority to resume normal succession, or (3) invoke a **distinct external recovery ceremony**. Never represent (3) as (2).

```text
RecoveryAnchor { affected_authority_key; last_verifiable_authority_frontier;
                 unrecoverability_evidence; external_authorization_proof; new_configuration_digest }
```
Recovery happens inside an existing history, so it preserves/acknowledges the last verifiable frontier even though ordinary continuity cannot be proven. Distinct from Genesis (first external introduction, #30): recovery is exceptional re-introduction when succession proof is impossible. Hardenings (vendor-A review): the anchor MUST carry **explicit evidence of unrecoverability** (proof the legitimate predecessor cannot form a quorum), require **external trust at least equal to** the authority it restores, and be a **distinct, auditable transition** — there must be **no path by which recovery masquerades as ordinary reconfiguration or silently lowers quorum** (S8). Otherwise the emergency anchor becomes exactly the permanent-master backdoor the contract exists to exclude. And the governing rule (ChatGPT PR-review): **recovery MUST be harder to invoke than a normal authority transition, never easier** — an attacker must gain nothing by deliberately forcing the system into recovery.

> **Continuity may fail; evidence of discontinuity must not.**

## 8. Core vs replaceable profile

- **Core obligations (this doc):** the S1–S9 contract, the succession relation, unique authoritative succession, the Receipt proof relationships + three-state verifier, content-addressed policy, the coordination-avoidance test, the recovery/genesis distinction.
- **Replaceable profile (#24, quarantined from Core vocabulary, enforced by the drift gate PR #35):** the consensus algorithm (Raft/HotStuff/PBFT/async-BFT/DAG-BFT), the reconfiguration construction (unique-successor / joint-consensus / statically-verifiable heterogeneous quorum — **but not** partial-order lattice/dominance, which is non-conforming per §4), the quorum-proof scheme (individual sigs + bitmap / accountable aggregate / accountable-threshold), the fault model (`3f+1` vs policy-dependent), and the coordination store engine.
- **kawa v0.1 reference profile (scored, PR #39; `formal/profile-scoring.md`):** BFT linear-epoch (HotStuff-/Tendermint-family) · comparability-preserving reconfiguration (unique-successor with cross-config quorum overlap, or joint-consensus) · **individual signatures + signer bitmap**. Alternative conforming profiles exhibited without a Core edit (gate 14): PBFT + explicit reconfiguration certificates; and accountable-aggregate BLS/MuSig2 + bitmap as the proof scheme. This is a Profile choice (§10), not Core.
- **Signer accountability is a Core requirement on the profile (sharpened, vendor-A review; confirmed by both scoring lanes):** a plain aggregate/threshold signature proves the quorum size but **erases individual culpability — it is therefore insufficient on its own** for blame assignment. The profile MUST use an **accountable-threshold scheme** or separately record the **signer-participation set** (which members signed), so a #21 distrust projection can attribute equivocation to specific members rather than surfacing an opaque protocol error. "Compact validity" and "attributable culpability" are distinct requirements; the slab requires both. Bare FROST/BLS/threshold group signatures are non-conforming.
- **The fault model is bound into the content-addressed policy (`policy_digest`), not merely into the profile (gate 21, owner synthesis).** A Cell whose policy declares a crash-only threat model MAY run a CFT (e.g. Raft) profile, but the **crash-only declaration MUST be part of the pinned `policy_digest`** so an offline verifier can see that a CFT Receipt was only ever valid under an explicit crash-only policy — a CFT Receipt can never be laundered into Byzantine authoritative standing. Without this binding, a per-cell CFT allowance is a downgrade-attack surface. BFT is the default; CFT is an explicit, policy-pinned exception.

**Conformance (the Ten-Year boundary, made testable):**
> **A consensus profile is conforming iff it preserves the S1–S9 Authority invariants and produces verifiable Receipts under its declared fault/synchrony model.**

Core semantics must not depend on selecting HotStuff / Tendermint / Raft-joint-consensus / a threshold scheme / a specific `3f+1` rule. **If replacing one profile with another forces a Core semantic rewrite, the abstraction boundary has failed** — and the freeze's principal risk is exactly that: *mechanics leaking back upward into the semantic slab.* Guard that boundary aggressively (§10 classes it; PR #35 enforces the vocabulary half).

## 10. Post-freeze change classes

Defined **now**, so that once frozen, new crypto/protocol/topology work cannot casually reopen Core (ChatGPT PR-review). Every future change to anything this slab touches declares its class:

```text
Core semantic change   — alters an invariant / authority standing / Receipt semantics.
                         Highest bar: full formal gate (§9) + independent adversarial review.
Profile change         — swaps the consensus / crypto / reconfiguration realization.
                         Must PROVE conformance (§8) to the UNCHANGED Core invariants; no Core edit.
Implementation change  — storage / runtime / performance mechanics only. No semantic effect.
Clarification          — wording; provably no behavioral change (drift gate PR #35 applies).
```

This is the operational form of *Stable semantics, replaceable mechanics*: a new consensus algorithm or signature scheme is a **Profile change** that must clear §8 conformance, and by construction cannot force a Core rewrite. If it would, it is misclassified — the change is really a Core semantic change and takes the highest bar.

## 11. Boundaries

This slab governs *where coordination is required, how the smallest authority domain agrees, and how that agreement is proven.* It does not define the **authorization model** (who may request/exercise authority — ocap/RBAC/ABAC/ReBAC/Zanzibar), which is deferred (R6) and must *consume* this boundary, not redefine it. It assumes the Receipt/Interpretation encoding of #36 and the emit `authority_key` serialization of #28/#18 (which this doc corrects to lock on `authority_key`, not `subject_ref`).
