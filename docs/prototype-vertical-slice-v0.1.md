# Kawa Comparative Prototype Vertical Slice v0.1

Status: Normative architecture gate experiment
Purpose: Resolve F-006 with implementation evidence rather than design preference.

## 1. Decision question

Implement the same bounded semantic vertical slice in two ways:

```text
A. Extend/refactor Memory Broker
B. Implement greenfield Kawa Core
```

The winning approach is the one that satisfies the same invariants with lower total structural complexity, lower migration risk, and clearer trust/SoT boundaries.

This experiment MUST NOT be used to justify production cutover.

## 2. Fixed vertical slice

Both candidates MUST implement exactly this semantic chain:

```text
deterministic Observation
→ Claim
→ Fact projection
→ Problem
→ Plan
→ adversarial Review
→ Finding
→ Plan revision
→ stale revision rejection
→ Result
```

The slice intentionally excludes broad UI, full federation, complete Git integration, general workflow DSL, and production secret brokering.

## 3. Canonical scenario

Use only synthetic data.

Scenario:

```text
Project: prj_example
Subject: res_example_service

1. deterministic collector observes:
   software.component.version = 1.2.3

2. accountable reasoning workload records Claim:
   software.component.risk = vulnerable
   based_on -> Observation

3. Fact projection derives current accepted risk from policy/evidence.

4. Problem is raised:
   vulnerable component requires remediation.

5. Plan is proposed:
   upgrade component to a non-vulnerable version.

6. independent reviewer raises HIGH Finding:
   rollback verification is missing.

7. Plan is revised to add rollback verification semantics.

8. a stale worker attempts to submit the earlier revision.
   system MUST reject with semantic conflict, not silently LWW.

9. reviewer completes successfully.

10. Result is recorded as a semantic outcome only; no real external side effect occurs in the prototype.
```

## 4. Shared acceptance tests

Both implementations MUST pass the same tests.

### A. Event / history

```text
A1. Durable semantic history is append-only.
A2. Correction/revision creates new durable history; prior records remain.
A3. Rebuilding current semantic state from durable inputs produces equivalent results.
A4. No ordinary current-state row is required as an unrebuildable Domain SoT.
```

### B. Observation / Claim / Fact

```text
B1. deterministic collector provenance is infrastructure/runtime-attached.
B2. ordinary LLM/Agent input cannot self-declare trusted collector identity.
B3. LLM inference is represented as Claim, not deterministic Observation.
B4. Claim does not automatically become Fact.
B5. conflicting evidence can produce explicit conflicted/unknown Fact state.
```

### C. Scope / authorization

```text
C1. omitted Project never widens access globally.
C2. unique trusted scope is inferred automatically.
C3. ambiguous authorized scope returns needs_selection.
C4. unauthorized objects cannot influence ranking or returned choices.
```

### D. Plan / Review

```text
D1. Plan survives author/reviewer process restart.
D2. HIGH open Finding blocks ready/start semantics.
D3. Review is bound to the Plan semantics it reviewed.
D4. revision preserves prior Plan history.
```

### E. stale-write correctness

```text
E1. two workers act from the same Plan basis.
E2. first accepted revision changes current Plan.
E3. second stale state-dependent revision is rejected.
E4. ordinary caller does not need to construct CAS/ETag/revision token.
E5. stale protection is bound to exact subject/action/work context.
```

### F. LLM-facing input minimization

```text
F1. new semantic refs are generated by trusted system path.
F2. identity/timestamp/schema/provenance bookkeeping is not caller-authored.
F3. fields uniquely implied by Work/context are omitted from required input.
F4. ambiguous semantic choices stop instead of being guessed.
```

### G. side-effect boundary

```text
G1. Event replay performs no external side effect.
G2. Result records outcome semantics; it is not proof that an external action occurred unless trusted execution evidence exists.
```

## 5. Memory Broker candidate constraints

The Memory Broker implementation MAY reuse its existing:

```text
plans/reviews/tasks
observation/evidence typing
watchers
idempotency
migration framework
HTTP/MCP surfaces
existing authorization/identity mechanisms
```

But it MUST demonstrate how the slice satisfies the shared acceptance tests without special pleading.

The experiment MUST record each legacy surface that must be modified or bypassed.

Do not score a pre-existing capability as a Kawa advantage merely because it already exists; score the adaptation cost and resulting architecture.

## 6. Greenfield Kawa candidate constraints

The Kawa implementation MUST remain intentionally small.

Minimum allowed persistent Domain shape:

```text
events
event_links
typed event-family payloads
```

Projection storage MAY be ephemeral/materialized as needed, but rebuildability must be demonstrated.

Do not implement unrelated roadmap features to make Kawa look more complete.

## 8. Qualitative scoring dimensions

Score each candidate 0–5, with evidence, on:

```text
semantic clarity
Event-only SoT fidelity
rebuildability
single-write-path fidelity
security/trust boundary clarity
LLM input simplicity
scope isolation
stale-write correctness
replication independence
migration blast radius
rollback simplicity
operational complexity
legacy compatibility burden
```

Scores without linked evidence are invalid.

## 9. Hard fail conditions

A candidate fails regardless of aggregate score if any of the following is true:

```text
current Domain state cannot be rebuilt from durable inputs
LLM can self-assert trusted provenance/identity
scope omission can widen visibility
state-dependent stale Plan write can silently overwrite current meaning
external side effects occur during Event replay
more than one authoritative Domain write language is required indefinitely
migration requires permanent bidirectional dual authority
```

## 10. Decision rule

After both candidates pass or fail the same tests:

```text
if only one passes hard invariants
→ choose that architecture

if both pass
→ choose the lower combined structural + migration + operational complexity

if Memory Broker extension is materially simpler
→ reopen greenfield assumption and evolve Broker toward Kawa semantics

if greenfield Kawa is materially simpler
→ close F-006 in favor of greenfield Kawa + bounded migration

if evidence is inconclusive
→ keep F-006 open and reduce/clarify the experiment; do not decide by preference
```

## 11. Independence rule

The implementation author MUST NOT be the only evaluator of the prototype outcome.

Before F-006 closes, an independent reviewer must inspect:

```text
both implementations
test evidence
measurement records
hard-fail evaluation
migration assumptions
```

The reviewer is instructed to refute the proposed winner.
